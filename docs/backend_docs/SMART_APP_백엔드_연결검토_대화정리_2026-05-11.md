## 5. 핵심 결론

백엔드 API 범위는 SMART_APP 점주 관리 앱과 연결 가능한 상태로 판단했다.

점주 앱 핵심 흐름인 로그인, 대시보드, 농장 관리, 상품 관리, ML 예측, 수확 슬롯, 예약/주문 조회, 발주 승인, 신선도 검사, 배송 등록, 반품/환불 결정, 점주 프로필 API가 대부분 구현되어 있었다.

다만 현재 Flutter 앱은 실제 백엔드 연결 준비가 일부만 되어 있다.

현재 앱에서 실제 HTTP 호출을 시도하는 곳은 대시보드 1곳이며, 그마저도 다음 문제가 있다.

- 호출 경로가 `/owner/dashboard`라서 실제 백엔드 경로 `/api/v1/owner/dashboard`와 다르다.
- 인증 토큰 저장과 `Authorization: Bearer <access_token>` 헤더 주입 구조가 없다.
- 백엔드 응답은 `data/message/error` 래퍼 구조인데 앱은 내부 `data`를 꺼내지 않는다.
- 백엔드는 snake_case 필드를 반환하지만 앱 모델은 camelCase 키를 읽는다.
- 로그인, 회원가입, 상품, 발주, 배송, 반품 등 대부분 화면은 더미 데이터와 로컬 상태 기반이다.

따라서 최종 판단은 다음과 같다.

| 항목 | 판단 |
|---|---|
| 백엔드 API 범위 | 연결 가능 |
| 현재 SMART_APP 코드 즉시 연결 | 부분 연결만 가능 |
| 바로 정상 동작 가능한 화면 | 없음에 가까움 |
| 필요한 작업량 | 중간 |
| 우선 작업 | 공통 API 클라이언트, 로그인/토큰 저장, 응답 래퍼 처리, 모델 매핑 |

## 6. 우선 수정이 필요한 지점

1. `lib/core/api_service.dart`
   - baseUrl에 `/api/v1` 포함
   - 인증 헤더 주입
   - `data/message/error` 응답 래퍼 처리
   - 401/403/422/500 에러 처리

2. 로그인 흐름
   - `POST /api/v1/auth/login` 호출
   - `access_token` 저장
   - `GET /api/v1/me`로 OWNER 계정 확인
   - 로그아웃 시 토큰 삭제

3. 대시보드 모델
   - `response['data']` 파싱
   - `open_slots`, `new_procurements`, `quality_waiting`, `ready_to_ship`, `return_requests`를 앱 필드로 매핑

4. 더미 데이터 화면
   - 상품, 발주, 배송, 반품, 프로필 화면을 Repository 기반 실제 API 호출로 교체
