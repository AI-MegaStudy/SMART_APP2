# SMART_APP - HARVEST-SLOT-BACKEND 연결 검토

작성일: 2026-05-11

목적: 점주 관리 앱 SMART_APP과 백엔드 HARVEST-SLOT-BACKEND 연결 가능 여부를 검토하고, 실제 연동 전에 맞춰야 할 항목을 정리한다.

## 1. 결론

현재 백엔드는 SMART_APP 점주 관리 앱과 연결 가능한 API 범위를 대부분 갖추고 있습니다.

점주 앱의 핵심 흐름인 로그인, 대시보드, 농장 관리, 상품 관리, ML 예측, 수확 슬롯, 예약/주문 조회, 발주 승인, 신선도 검사, 배송 등록, 반품/환불 결정, 점주 프로필 API가 `/api/v1/owner/...` 기준으로 구현되어 있습니다.

다만 현재 SMART_APP Flutter 코드는 실제 백엔드 연결 준비가 일부만 되어 있습니다.

- 앱에서 실제 HTTP 호출을 시도하는 곳은 현재 대시보드 1곳입니다.
- 대시보드 호출 경로가 `/owner/dashboard`라서 백엔드 실제 경로 `/api/v1/owner/dashboard`와 맞지 않습니다.
- 인증 토큰 저장 및 `Authorization: Bearer <access_token>` 헤더 주입 구조가 아직 없습니다.
- 백엔드 응답은 `data, message, error` 래퍼 구조인데, 앱 모델은 내부 `data`를 꺼내지 않고 바로 화면 모델로 파싱합니다.
- 백엔드는 snake_case 필드를 반환하지만 앱 일부 모델은 camelCase 키를 읽고 있어 매핑 수정이 필요합니다.
- 로그인, 회원가입, 상품, 발주, 배송, 반품 등 대부분 화면은 현재 정적 데이터와 로컬 상태 중심입니다.

따라서 최종 판단은 다음과 같습니다.

| 항목 | 판단 |
|---|---|
| 백엔드 API 범위 | 연결 가능 |
| 현재 SMART_APP 코드 즉시 연결 | 부분 연결만 가능 |
| 바로 정상 동작 가능한 화면 | 없음에 가까움. 대시보드도 경로/인증/응답 파싱 수정 필요 |
| 필요한 작업량 | 중간 |
| 우선 작업 | 공통 API 클라이언트, 로그인/토큰 저장, 응답 래퍼 처리, 모델 매핑 |

## 3. 공통 응답 구조

백엔드는 일반 API 응답을 아래 구조로 반환합니다.

```json
{
  "data": {},
  "message": "success",
  "error": null
}
```

SMART_APP의 Repository에서는 화면 모델로 변환하기 전에 반드시 `data` 내부 값을 꺼내야 합니다.

현재 `lib/core/api_service.dart`는 전체 JSON을 그대로 반환하고, `DashboardRepository`는 그 값을 바로 `DashboardModel.fromJson()`에 전달합니다. 이 구조에서는 실제 대시보드 값이 아니라 래퍼 객체를 읽게 됩니다.

수정 방향:

```dart
final response = await ApiService.get('/owner/dashboard');
final data = response['data'] as Map<String, dynamic>;
return DashboardModel.fromJson(data);
```

또는 `ApiService`에서 공통으로 `data`만 반환하게 만들 수 있습니다.

## 4. 인증 연결 방식

점주 앱 로그인은 아래 API를 우선 사용하면 됩니다.

```text
POST /api/v1/auth/login
```

요청 예시:

```json
{
  "email": "owner@test.com",
  "password": "demo1234!"
}
```

응답의 `data.access_token`을 저장한 뒤, 점주 API 호출에 아래 헤더를 붙여야 합니다.

```text
Authorization: Bearer <access_token>
```

현재 SMART_APP에는 다음 구조가 없습니다.

- 로그인 API 호출
- access token 저장소
- 앱 재실행 시 토큰 복원
- API 요청 시 Authorization 헤더 자동 주입
- 401 응답 시 로그인 화면 이동

이 작업이 되지 않으면 `/owner/...` API는 대부분 `authentication required` 또는 `forbidden`으로 실패합니다.

## 5. 현재 앱 코드와 백엔드의 주요 불일치

### 5.1 Base URL과 prefix

현재 앱:

```dart
static const String baseUrl = 'http://127.0.0.1:8000';
ApiService.get('/owner/dashboard');
```

백엔드 실제 경로:

```text
http://127.0.0.1:8000/api/v1/owner/dashboard
```

수정 방향:

```dart
static const String baseUrl = 'http://127.0.0.1:8000/api/v1';
```

실기기 또는 Android 에뮬레이터에서 테스트할 경우 `127.0.0.1`은 앱 실행 기기 자신을 가리키므로 환경별 주소 분기가 필요합니다.

| 실행 환경 | 권장 주소 |
|---|---|
| Flutter macOS/desktop | `http://127.0.0.1:8000/api/v1` |
| iOS Simulator | `http://127.0.0.1:8000/api/v1` |
| Android Emulator | `http://10.0.2.2:8000/api/v1` |
| 실제 기기 | 같은 네트워크의 개발 PC IP 사용 |

### 5.2 대시보드 필드명

백엔드 응답:

```json
{
  "open_slots": 6,
  "new_procurements": 4,
  "quality_waiting": 7,
  "ready_to_ship": 3,
  "return_requests": 2
}
```

현재 앱 모델이 읽는 키:

```text
openSlots
newProcurements
inspectionWaiting
readyToShip
returnRequests
```

수정 방향:

| 앱 필드 | 백엔드 필드 |
|---|---|
| `openSlots` | `open_slots` |
| `newProcurements` | `new_procurements` |
| `inspectionWaiting` | `quality_waiting` |
| `readyToShip` | `ready_to_ship` |
| `returnRequests` | `return_requests` |

### 5.3 상품 상태값

백엔드 상품 상태:

| 백엔드 상태 | 앱 표시 |
|---|---|
| `ACTIVE` | 판매 중 |
| `HIDDEN` | 준비 중 또는 숨김 |
| `SOLD_OUT` | 판매 중지 또는 품절 |

현재 앱은 `판매 중`, `준비 중`, `판매 중지` 한글 문자열을 내부 상태로 직접 사용합니다. API 연결 시 백엔드 enum과 화면 표시값을 분리해야 합니다.

### 5.4 수확 슬롯 상태값

백엔드 상태:

| 백엔드 상태 | 앱 표시 |
|---|---|
| `DRAFT` | 작성 중 |
| `OPEN` | 예약 가능 |
| `CLOSED` | 마감 |

### 5.5 발주 상태값

백엔드 상태:

| 백엔드 상태 | 앱 표시 |
|---|---|
| `REQUESTED` | 승인 대기 |
| `APPROVED` | 승인 |
| `PARTIAL_APPROVED` | 부분 승인 |
| `REJECTED` | 거절 |

현재 앱은 발주 승인 페이지에서 `sampleOrders` 기반 로컬 데이터를 재사용합니다. 실제 연결 시 `GET /owner/procurements` 응답의 `items` 구조를 기준으로 화면 모델을 새로 만드는 것이 좋습니다.

### 5.6 신선도 검사 API

현재 앱 `QualityPage`는 갤러리에서 이미지를 선택하고 미리보기와 가이드 UI를 보여주지만, 백엔드 업로드/분석 API 호출은 없습니다.

백엔드에서 사용할 수 있는 방식은 두 가지입니다.

```text
POST /api/v1/owner/quality-inspections/analyze
```

- multipart: `procurement_item_id`, `image`
- json: `procurement_item_id`, `image_url`, `persist_image`

```text
POST /api/v1/owner/quality-inspections
```

- 분석/업로드 결과를 확정 검사 기록으로 저장

앱 화면에는 먼저 발주 품목 선택이 필요합니다. 현재는 이미지 선택만 있고 `procurement_item_id` 선택 흐름이 없습니다.

## 6. 기능별 연결 메모

### 6.1 로그인/회원가입

백엔드는 `POST /api/v1/auth/owners/signup`, `POST /api/v1/auth/login`을 제공합니다.

현재 앱의 로그인은 입력값 검증 후 바로 `Home`으로 이동합니다. 회원가입도 로컬 중복 검사와 폼 검증 중심입니다.

필요 작업:

- `AuthRepository` 추가
- 로그인 성공 시 token 저장
- 회원가입 후 이메일 인증 흐름 연결
- `GET /api/v1/me`로 로그인 사용자 role 검증
- `OWNER`가 아닌 계정 차단

### 6.2 대시보드

백엔드 API는 준비되어 있습니다.

```text
GET /api/v1/owner/dashboard
```

앱도 Repository/ViewModel 구조가 이미 있으므로 가장 먼저 실제 연결하기 좋은 화면입니다.

필요 작업:

- API prefix 수정
- Authorization 헤더 추가
- `response['data']` 파싱
- snake_case 필드 매핑
- 실패 시 무조건 demo 데이터로 숨기지 말고 개발 단계에서는 오류 표시 또는 로그 출력

### 6.3 농장 관리

백엔드 API:

```text
GET /api/v1/owner/farms/me
PUT /api/v1/owner/farms/{farm_id}
```

현재 앱은 `FarmDetailPage`에 정적 초기값이 들어 있습니다.

필요 작업:

- 점주 농장 목록 조회 후 첫 농장 또는 선택 농장 표시
- 수정 요청 payload를 백엔드 필드에 맞춤
- 농장 이미지 업로드가 필요하면 별도 이미지 API 또는 URL 입력 정책 결정

### 6.4 상품 관리

백엔드 API:

```text
GET /api/v1/owner/products
POST /api/v1/owner/products
PUT /api/v1/owner/products/{product_id}
POST /api/v1/owner/products/{product_id}/image
PATCH /api/v1/owner/products/{product_id}/status
```

현재 앱은 `ProductRecord`와 로컬 리스트로 등록/수정/삭제처럼 보이는 흐름을 구현해 둔 상태입니다.

필요 작업:

- `ProductModel`에 `product_id`, `farm_id`, `fruit_type`, `variety`, `package_unit_kg`, `base_price`, `product_status`, `image_url` 반영
- 삭제 기능은 백엔드에 별도 `DELETE`가 없으므로 `PATCH status`로 숨김/판매중지 처리할지 결정
- 앱의 `stockKg`는 백엔드 상품 자체 필드가 아니라 수확 슬롯의 예약 가능 수량과 연결하는 편이 맞음

### 6.5 ML 예측/수확 슬롯

백엔드 API:

```text
POST /api/v1/owner/ml/predictions
GET /api/v1/owner/ml/predictions
GET /api/v1/owner/ml/predictions/{prediction_id}
GET /api/v1/owner/harvest-slots
POST /api/v1/owner/harvest-slots
PUT /api/v1/owner/harvest-slots/{slot_id}
PATCH /api/v1/owner/harvest-slots/{slot_id}/status
```

현재 앱 `HarvestSlotPage`는 `_predictions` 정적 데이터로 예측 결과를 보여줍니다.

필요 작업:

- 농장/상품 선택값을 실제 `farm_id`, `product_id`로 연결
- ML 예측 생성 요청의 `features` 입력 UI 정의
- 예측 결과를 수확 슬롯 생성 payload로 넘기는 흐름 구현
- 슬롯 상태 `DRAFT`, `OPEN`, `CLOSED` 표시 매핑

### 6.6 예약/주문 현황

백엔드 API:

```text
GET /api/v1/owner/reservations
GET /api/v1/owner/orders
```

현재 앱 `OrdersPage`는 `sampleOrders` 정적 데이터를 사용합니다.

필요 작업:

- 예약과 주문을 분리해서 볼지, 현재처럼 하나의 현황 화면에서 합쳐 볼지 결정
- 주문 상태 enum을 한글로 표시하는 mapper 추가
- 상품/슬롯/고객/금액/일시 필드 기준 화면 모델 추가

### 6.7 발주 승인

백엔드 API:

```text
GET /api/v1/owner/procurements
GET /api/v1/owner/procurements/{procurement_id}
PATCH /api/v1/owner/procurements/{procurement_id}/decision
```

승인 요청 예시:

```json
{
  "decision": "APPROVED",
  "items": [
    {
      "procurement_item_id": 1,
      "approved_package_count": 2,
      "approved_kg": 10.0,
      "owner_memo": "정상 수량 확인"
    }
  ],
  "rejected_reason": null
}
```

현재 앱은 여러 발주를 선택해서 일괄 승인/거절하는 UI처럼 동작합니다. 백엔드 API는 `procurement_id` 단위 결정이므로 일괄 처리는 프론트에서 여러 PATCH를 순차 호출하는 방식으로 구현해야 합니다.

### 6.8 배송 관리

백엔드 API:

```text
POST /api/v1/owner/shipments
PATCH /api/v1/owner/shipments/{shipment_id}/status
```

배송 등록 요청 예시:

```json
{
  "order_id": 1,
  "carrier_name": "CJ대한통운",
  "tracking_no": "1234567890",
  "shipped_package_count": 2,
  "shipped_kg": 10
}
```

현재 앱은 승인된 발주 현황의 로컬 문자열을 파싱해서 배송 상품을 만듭니다. 실제 연결 시 `procurements` 또는 `orders` 응답에서 `order_id`를 명확히 가져와야 합니다.

### 6.9 반품/환불 관리

백엔드 API:

```text
GET /api/v1/owner/returns
PATCH /api/v1/owner/returns/{return_request_id}/decision
```

반품 결정 요청 예시:

```json
{
  "decision": "APPROVED",
  "approved_amount": 39000,
  "decision_reason": "반품 승인 및 환불 완료"
}
```

현재 앱은 반품 요청과 처리 결과를 로컬 리스트로 관리합니다. 실제 연결 시 반품 목록 조회 후 상세/승인/거절 결과를 서버에 반영해야 합니다.

### 6.10 점주 프로필

백엔드 API:

```text
GET /api/v1/owner/profile
PUT /api/v1/owner/profile
```

수정 가능 필드:

```json
{
  "owner_name": "김하늘",
  "owner_phone": "01022223344",
  "business_number": "3124567890"
}
```

현재 앱 `OwnerDetailPage`에는 이메일과 비밀번호 입력도 있습니다. 백엔드의 점주 프로필 수정 API는 이메일/비밀번호 변경을 포함하지 않습니다.

## 7. 백엔드 추가 또는 정리가 필요한 부분

### 7.1 비밀번호 찾기/재설정 API

현재 SMART_APP에는 `PasswordFindPage`가 있지만 백엔드에는 비밀번호 재설정 전용 API가 보이지 않습니다.

권장 API:

```text
POST /api/v1/auth/password/reset/request
POST /api/v1/auth/password/reset/confirm
```

이메일 인증의 `RESET_PASSWORD` purpose가 이미 정의되어 있으므로 이를 활용할 수 있습니다.

### 7.2 이메일 찾기 API

현재 SMART_APP에는 `EmailFindPage`가 있습니다. 이름과 전화번호로 이메일을 찾는 기능을 실제 제공하려면 별도 API가 필요합니다.

권장 API:

```text
POST /api/v1/auth/email/find
```

요청 예시:

```json
{
  "name": "김하늘",
  "phone": "01022223344",
  "role": "OWNER"
}
```

### 7.3 상품 삭제 정책

앱에는 상품 삭제 모드가 있지만 백엔드에는 `DELETE /owner/products/{product_id}`가 없습니다.

운영 관점에서는 주문/슬롯 이력이 있는 상품을 물리 삭제하기보다 아래 중 하나가 적합합니다.

- 기존 `PATCH /owner/products/{product_id}/status`로 `HIDDEN` 처리
- 별도 `ARCHIVED` 상태 추가
- 삭제 UI 문구를 "판매 숨김" 또는 "판매 중지"로 변경

### 7.4 농장 이미지 업로드

상품 이미지와 신선도 이미지는 업로드 API가 있지만, 농장 이미지 전용 업로드 API는 명확하지 않습니다. 현재 `PUT /owner/farms/{farm_id}`는 `farm_image_url` 문자열을 받을 수 있습니다.

권장 방향:

- 기존 공통 이미지 API를 사용해 URL을 만든 뒤 `farm_image_url` 저장
- 또는 `POST /api/v1/owner/farms/{farm_id}/image` 추가

### 7.5 백엔드 실행/배포 준비 파일

현재 `backend` 폴더 안에서 `requirements.txt`, `pyproject.toml`, 실행 README, DB migration 파일은 확인되지 않았습니다.

코드는 현재 환경에서 import 가능하지만, 신규 환경에서 백엔드를 실행하려면 아래 정리가 필요합니다.

- Python 의존성 파일
- `.env.example`
- DB 생성/마이그레이션/시드 절차
- 테스트 계정 안내
- 로컬 실행 명령

### 7.6 Swagger 문서 한글 깨짐

`backend/app/main.py`의 description 문자열에 한글 깨짐이 보입니다. Swagger 품질을 위해 UTF-8 문자열로 정리하는 것이 좋습니다.

## 9. 최종 판단

백엔드의 점주 관리 API는 SMART_APP 화면 정의서와 큰 방향이 잘 맞습니다. API 자체는 연결 가능한 상태로 판단됩니다.

하지만 현재 SMART_APP은 대부분 화면이 더미 데이터와 로컬 상태 기반이고, 실제 네트워크 계층은 대시보드 일부만 존재합니다. 따라서 "백엔드가 없어서 못 붙는 상태"라기보다 "앱 쪽 연동 계층과 모델 매핑을 아직 만들어야 하는 상태"에 가깝습니다.

바로 착수한다면 대시보드부터 연결하는 것이 가장 안전합니다. 이후 로그인/토큰 저장을 붙이고, 상품/발주/배송/반품 순서로 더미 데이터를 Repository 기반 실제 데이터로 교체하면 됩니다.
